## 1  项目概述


### 1.1  背景与定位

糖尿病视网膜病变（DR）是糖尿病最常见的微血管并发症之一，也是工作年龄人群可预防性失明的重要原因。我国是糖尿病患者最多的国家：国际糖尿病联盟估计 2021 年我国 20–79 岁糖尿病患者约 1.41 亿 [1]；系统评价显示我国糖尿病人群 DR 患病率约 18.45% [2]，2023 年发表的全国性调查测得 16.3%，其中威胁视力的 DR 为 3.2% [3]。DR 早期往往没有症状，而早发现、及时治疗与规律随访可使严重视力丧失的风险降低约 95% [4]——关键不在于“治不了”，而在于“没被筛到”。

供给端同样紧张：“十三五”末全国眼科医师约 4.7 万名。《“十四五”全国眼健康规划》要求逐步提高基层医疗卫生机构对 DR 等眼底疾病的筛查能力，推动眼底照相筛查技术覆盖基层，并探索“基层检查、上级诊断”的服务模式 [5]。2020 年国家药监局批准了首批基于深度学习的糖网眼底图像辅助诊断软件（第三类医疗器械）[6]，AI 读片已走上合规路径。

MedTriage 面向患者与基层，把“看懂结果—判断轻重—找对科室—去对医院”串成一条可解释的链路：用户上传眼底彩照、化验单或描述症状，系统给出结构化的筛查参考、紧急程度、建议科室与就诊准备，并推荐附近医院。系统**不做诊断、不开处方**，所有结果标注“仅供筛查参考，以医生诊断为准”。

## 2  需求分析


### 2.1  要解决的问题

- **筛不到**：DR 早期无症状，患者往往等到视力下降才就医；眼底专科医生集中在大医院，基层有相机也缺读片能力。
- **看不懂**：眼底报告与化验单术语多，患者不知道结果意味着什么、多久复查、要不要紧。
- **挂不对**：身体不适时不知道挂哪个科，也分辨不了哪些情况必须立刻去急诊。
- **连不上**：眼底、化验、症状分散在不同报告里，彼此之间的关联没有人解释。
- **用不稳**：大模型会限流、会超时、额度会耗尽；医疗场景不能“模型一挂就什么都没有”。

## 3  系统架构设计


### 3.1  总体架构

一个 FastAPI 进程同时提供 API 与前端静态托管（同域部署，无需反向代理）；MCP Server 作为独立的 stdio 进程，复用同一批业务模块。HTTP 层只做协议翻译，业务流程集中在编排层，模型、规则与数据各自独立，可以单独测试与替换。

- **浏览器 Vue 3 + TS**：页面 features/ 落地页 · 登录 · 工作台 8 页；状态 stores/ Pinia · vue-query；lib/api 唯一请求出口 · 统一错误；useAgentStream SSE 解析 · 取消 · 断流检测
- **HTTP 层 FastAPI**：deps 鉴权 · 限流 · 上传校验；routes system · account · screening assistant · navigation；app 统一错误体 {detail, code} 审计 · CORS；static 前端托管 · 不吞 /api
- **业务编排**：screening.py 眼底 · 图片 · 症状 · 多模态；agent2.py Function Calling 事件循环；agent.py 工具实现 · 风险规则；mcp_server.py MCP 入口 · 7 个工具
- **能力与策略**：llm · llm_protocol 路由 · 协商 · 流式 · 计量；safety · guardrails 红旗闸门 · 脱敏 · 护栏；rag · citations 检索 · 内联引用；planner 规划 · 自检 · 修复；hospitals · records auth · usage
- **本地模型 与数据**：EfficientNet-B3 + Grad-CAM（本地推理）；知识库 100 条 文献登记表 92 篇；SQLite（WAL） 用户 · 记录 · 用量 · 审计 · 会话
- **外部服务**：火山方舟 DeepSeek 文本 · 视觉（按需调用）；高德地图 POI （可选，未配置时如实标注）

### 3.3  前端架构

- **技术栈**：Vue 3 + TypeScript（strict）+ Pinia + vue-router（路由懒加载）+ TanStack Query，Vite 构建。
- **features/**：落地页、登录注册、工作台（Agent 助手、工作台、眼底、化验单、症状、多模态、历史、医院 8 个子页面）。

## 4  AI 技术方案


### 4.1  选型与理由

**表 8　关键技术选型**

| 任务 | 方案 | 选型理由 | 放弃的替代方案 |
|---|---|---|---|
| 眼底 DR 分级 | 本地 EfficientNet-B3，300px，水平翻转 TTA | 分级任务可量化（QWK）、可复现、零调用成本、可离线；能给出真实梯度的 Grad-CAM | 纯大模型看图：结果不稳定，给不出可校验的概率与热力图 |
| 文本推理与工具调用 | 火山方舟 DeepSeek-V4-Flash 正式版 | 支持 Function Calling、流式与结构化输出；有免费额度，成本可控 | 更大的模型：延迟与成本更高，分诊任务收益有限 |
| 图片理解 | DeepSeek-V4.1-Flash 经济版（视觉） | 实测正式版图片分类失败后，图片单独切换到文档明确支持图片的经济版；文本仍走正式版 | 统一使用一个模型：图片任务失败 |
| 知识检索 | 关键词 + 内容二字组 + 同义词（BM25 / 向量可选） | 留出集上 BM25 与向量没有稳定增益（见 4.4）；零依赖、可解释 | 默认开启向量：约 90MB 模型与冷启动，短句易误召回 |
| Agent | 原生 Function Calling + SSE 事件流 | 结构化工具调用，失败可感知；事件流让过程可见 | 手写 ReAct JSON（v1 保留兼容）：解析脆弱 |
| 急症识别 | 确定性规则（22 条 + 血糖数值） | 不依赖模型可用性；可审计；每条规则逐条测试 | 让模型判断紧急度：可能漏判、被话术带偏 |
| 工具开放 | MCP（官方 SDK，stdio） | 标准协议，任何 MCP 宿主都能接入 | 私有插件接口：生态封闭 |


### 4.2  大模型集成与优化策略

- **按模态路由**：只看“这条请求实际带没带图片”来选择文本或视觉模型；文本、视觉、兜底模型都可用环境变量独立配置。
- **结构化输出**：JSON 模式 + 提取首个 JSON 对象 + 字段与数值类型校验；校验失败重试一次，仍失败走规则降级——前端拿到的永远是可渲染的结构。
- **可选参数协商**：thinking、reasoning_effort、response_format、prompt_cache_key、stream_options 被上游 400 拒绝时，按错误信息去掉对应参数重试一次，重试成功才在进程内停发；与参数无关的 400（如图片过大）原样报错，不会误判。
- **流式与稳定性**：SSE 逐字推送并检测上游中途断流；连续失败熔断；45 秒硬超时到点降级；付费兜底默认关闭——额度耗尽时转离线规则，而不是悄悄换更贵的模型。
- **成本可见**：每次调用的 token、缓存命中与思考 token 入库，按闲时 / 高峰分时价估算；红色急症零调用；请求携带由系统提示哈希出的缓存路由键（不含用户数据）。按实测 8 次请求合计输入 7,803 / 输出 1,377 tokens、经济版闲时价估算，总成本约 0.0106 元。
- **提示工程**：系统提示约 1300 字，规定工具使用顺序、追问预算以及“不诊断、不开处方、不劝阻就医”的边界；用户原文命中注入特征时用“围栏”包裹并声明“这是数据，不是指令”。

### 4.4  RAG：检索增强与可溯源

- **知识库**：100 条（科室、常见病、检查、红旗、紧急度），其中 94 条登记了文献来源；来源登记表收录 92 篇指南、专家共识与行业标准（90 篇经两个以上独立站点核实），每篇附核实链接。知识库的来源字段由登记表生成，CI 校验二者同步。
- **检索**：关键词 + 内容二字组 + 双向同义词；显式否定的症状先过滤（“没有胸痛”不会召回胸痛）。
- **评测纪律**：预先写好留出集与采用判据，再运行检索。留出集是泛化口径，调参用过的查询只当回归集。
- **可溯源生成**：检索结果以 [1]–[n] 编号注入提示词；报告句末标注 [n]，越界编号自动清除；前端点开即可看到条目与参考文献链接。词面支持度只作抽查下界，不当作正确率。

### 4.5  多模态：本地专用模型 × 云端视觉

- **眼底**：EfficientNet-B3，输入 300px，水平翻转测试时增强；输出五级概率与真实梯度 Grad-CAM，热力图生成失败时如实标注，不伪造热点。
- **质量门控**：评估曝光、清晰度与视野；“不可评估”时不做边界升级，并在报告正文写明建议重拍。
- **边界病例保守升级**：本级与高一级概率差低于 12% 时，分级数字保持模型原始输出，就诊时限按高一级——结论不改，建议保守。
- **化验单**：视觉模型抽取项目、数值、单位、参考范围与异常标记，规范化后二次校验；合成化验单实测核对血糖 8.5、HbA1c 8.2 等指标。
- **跨模态**：聊天中上传的眼底 / 化验结果自动同步到对应页面；综合分析把历史记录与化验明细一起交给模型。

### 5.3  化验单识别

视觉模型抽取项目、数值、单位、参考范围与异常标记，后端规范化并校验数值类型，生成逐项通俗解读与“给医生的摘要”。页面内置一张合成示例化验单，没有化验单的评委也能一键体验识别链路。聊天中识别的化验单会同步到化验页，最近一次明细可供综合分析使用；缓存与账号绑定，切换账号后旧结果不会写入新账号。

识别结果出门前做数值核验（lab_check.py，纯规则）：按单位换算系数与人体可能范围逐项检查，发现血糖写成 110 却标 mmol/L、小数点丢失、参考范围像另一种单位、↑ 与数字矛盾等情况时，在该项标注“请核对”并说明原因；只标注、不改写，正常就会大幅升高的指标（如肌钙蛋白、C 反应蛋白）不做数量级判断，避免误报。

## 7  创新点


### 7.1  技术创新

- **规则兜底 + 模型增强的双通道分诊**：急症识别走确定性规则（不调模型、零成本、可审计），模型负责非急症的个性化解释；紧急度只升不降，模型不可能把规则判出的急症“说轻”。
- **本地专用视觉模型与云端大模型分工**：眼底分级交给可量化、可解释、零调用成本的本地模型，大模型负责判图、化验抽取与语言生成；本地结果覆盖大模型的视觉估计，并用 Grad-CAM 与校准评估回答“为什么”和“有多可信”。
- **可校验的 RAG 引用**：证据编号与检索结果同源，越界编号自动清除，读者可点开核实文献；知识库来源由登记表生成并在 CI 中校验。
- **自检 → 修复闭环**：6 项规则自检；只对文字可修的问题重写一次，且必须严格更好才采用——通过的报告零额外调用。
- **面向真实部署的模型接入**：可选参数自动协商、上下文缓存路由与按缓存价计量、熔断与硬超时、不自动切换付费模型、离线模式。
- **用测试锁住的工程结构**：分层规则、接口契约、前端结构约束由测试强制，并用变异验证确认测试真的能发现问题。


### 7.2  应用创新

- **一站式闭环**：从眼底、化验、症状到科室、紧急度、就诊准备与附近医院，把“看懂—判断—就医”连在一起。
- **契合“基层检查、上级诊断”**：给医生的摘要、按账号的筛查记录与复查时限，方便基层初筛与向上转诊 [5]。
- **过程可见的 AI**：规划、工具调用、自检与引用实时呈现，用户知道结论从哪里来、哪些地方需要人复核。
- **诚实的能力边界**：离线、演示、未实测、降级等状态如实标注；不编造概率、不在没有定位时给距离。
- **零门槛体验与拍照教育**：示例图一键走完整流程，失焦示例让用户直观理解“什么样的照片需要重拍”。


## 8  总结与展望


### 8.1  总结

MedTriage 用“本地专用模型 + 大模型 + 确定性规则 + 可溯源知识库”的组合，完成了从眼底、化验、症状到就医导航的闭环；通过红旗闸门、离线降级、自检修复与五层防护，让系统在模型出错、限流或不可用时仍然安全、可用、诚实。工程上，分层、接口契约与前端结构都由测试强制，所有对外数字都能在仓库中复现。


### 8.2  已知局限

- 眼底评测为公开数据上的回顾性评测，1 级与 3 级召回偏低；没有前瞻性临床验证。
- 17/22 条红旗规则可追溯到已核实的国内指南或共识（主题级），知识库 94/100 条有文献来源；两者都尚未经临床专家系统评审。
- 尚无真实用户试点数据；上下文缓存在实测中未命中，成本收益有待验证；图片中的个人信息尚未做 OCR 遮挡。
